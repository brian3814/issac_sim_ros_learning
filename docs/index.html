01The idea

One thing to understand before anything else.

Isaac Sim does not “run ROS 2 code”. It evaluates a dataflow graph — OmniGraph — that PhysX ticks every frame, and some nodes in that graph happen to be DDS publishers and subscribers. There is no Python loop pumping messages.

That has a consequence worth the whole exercise: the code on your side of the wire is an ordinary ROS 2 node. It cannot tell whether a simulator or a real AMR is on the other end. Point it at real hardware publishing the same topics and it runs unchanged.

Nothing is installed on your machine. Isaac Sim vendors a complete minimal ROS 2 — rclpy, the message packages, tf2, even the ros2 CLI — under exts/isaacsim.ros2.bridge/humble/. The scripts add that to their own sys.path, so both sides of the wire use identical libraries and no version mismatch is possible.

05Frames

Two different publishers build the TF tree, and they meet at base_link.

One known nuance. ROS convention (REP-103) expects camera optical frames with +Z forward and +Y down, while the USD camera here is +X forward, +Z up. If you feed this into a perception stack that assumes optical frames, publish a static transform between front_camera and a front_camera_optical frame — rotating the camera prim instead would also rotate the rendered image.

run\scene.cmd --spin --save

:: lesson 3-4 — the bridge (terminal 1, then terminal 2)
run\sim.cmd
run\client.cmd monitor
run\client.cmd teleop
run\client.cmd patrol
run\client.cmd ros2 topic hz /scan

:: lesson 5 — labelled dataset
run\dataset.cmd --frames 40

In the Isaac Sim editor

run\sim.cmd without --headless already opens the full editor. To build the scene from Isaac Sim’s own Script Editor instead:

import sys
sys.path.insert(0, r"D:\code\omniverse_learn\ros2_integration")
from warehouse_amr import gui
gui.build()          # then press Play

That needs a separate entry point for two reasons: inside the GUI, Kit is already running so a second SimulationApp is not allowed, and the GUI owns the update loop so anything needing a frame to settle must await the next update rather than call simulation_app.update(). Hence gui.build() is asynchronous and returns immediately.

The drive figure is the one that matters. Topics being advertised only proves the graph was built; it says nothing about whether a Twist reaches PhysX. Phase 2 of the self-test publishes /cmd_vel, measures elapsed simulation time, and compares the odometry against the distance that command should have produced.

Why simulation time, not step count. One step(render=True) advances physics as many times as it needs to hit rendering_dt — twice, at 60 Hz physics and 30 Hz rendering. Counting steps reports double the real duration, which is exactly the trap that made an early version of this test claim a 200% result.

09Field notes

Four bugs hit while building this, each of which cost real time. All measured.

  1. Joint limits silently locked the wheels

    In UsdPhysics, physics:lowerLimit and physics:upperLimit default to ∓infinity — exactly what a continuously rotating wheel needs. Authoring a reversed pair (lower=1, upper=-1) as an “unlimited” idiom hands PhysX an impossible range and the joint locks solid.

    The symptom is maddening because everything upstream looks perfect: the subscriber receives the Twist, the controller emits the right wheel speeds, the articulation controller accepts them — and the wheels report a velocity of exactly zero.

    Fix Author no limit attributes at all on a wheel joint.

  2. UsdGeom.Cylinder colliders do not collide

    The obvious wheel primitive produces no usable PhysX collider here. The robot sinks until its chassis rests on the floor — exactly one wheel-radius too low — and spins buried wheels at the commanded velocity. Measured on flat ground, all commanded to 0.5 m/s for 6 s:

    Wheel primitiveDistance
    UsdGeom.Cylinder0.000 m
    UsdGeom.Capsule2.942 m
    UsdGeom.Sphere2.939 m

    Fix Use a capsule — a cylinder with rounded ends, natively supported.

  3. Frictionless casters stole the load

    Two casters plus two wheels is a statically indeterminate four-point contact, and the solver can put most of the normal force on the frictionless casters, leaving the drive wheels to spin with no grip.

    Fix Hold the casters 4 mm clear of the floor so the wheels carry the weight and the casters only catch a pitch.

  4. PowerShell launchers swallowed their own output

    A PowerShell function returns everything it emits, so exit (Invoke-IsaacPython ...) consumed the simulator’s entire console output as a return value — and exited immediately, orphaning a multi-gigabyte kit.exe.

    Fix Emit nothing from the function and read $LASTEXITCODE at the call site.

Two more worth knowing

Do not read poses off the USD stage while playing. Isaac Sim writes physics results into Fabric for speed; the USD attributes can lag or never update. ComputeLocalToWorldTransform() will happily return a plausible, wrong number. Use Articulation.get_world_poses() instead.

Ray-tracing shader compilation is host-RAM hungry, not VRAM hungry. Isaac Sim logs what it found at start-up — Max allowing 3 shader compiler sessions based on 6.1 GB of free system memory — and can be taken down by an LLVM ERROR: out of memory during the first rendered frames if that number is low.

Isolation

The project installs nothing and exports nothing. config.py writes os.environ — a per-process copy — but never reads it for configuration. The launchers set no variables at all. The DDS domain comes from .env on both sides (ROS2Context is created with useDomainIDEnvVar = False, and clients pass domain_id straight to rclpy.init()), so a stale ROS_DOMAIN_ID in some terminal cannot put the two halves on different domains.

The one gap in Isaac Sim’s vendored ROS 2 — a missing netifaces, which ros2cli.daemon imports unconditionally — is filled by a ~90-line stand-in registered in sys.modules rather than by installing a package.
