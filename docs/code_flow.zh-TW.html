Warehouse AMR · Isaac Sim 5.1 · ROS 2 Humble · 程式運作原理

程式在哪裡跑、怎麼啟動、按下 WASD 之後發生什麼

給要在這個 repo 上開發 digital twin 的人：說明哪些程式碼跑在 Omniverse（Kit）裡、哪些不是， run\sim.cmd 的每一步做了什麼，以及一個按鍵從鍵盤到 PhysX 輪子、再以 /odom 回到你的程式的完整路徑。

  • 兩個行程，靠 DDS 相連Isaac Sim（Kit）是一個行程，teleop／patrol 是另一個。兩者之間只有 ROS 2 topic，沒有共用記憶體。
  • Python 只負責「建構」你的 Python 寫 USD、建 OmniGraph，之後只呼叫 step()。每幀的 ROS 收發、控制、物理都是 Kit 裡的 C++ 在跑。
  • .env 是唯一的設定來源兩邊都從 .env 讀 DDS domain、輪徑、速度上限，所以兩邊一定一致。

01執行範圍：哪些在 Omniverse 裡跑

最重要的一張圖。左邊的大框是 Isaac Sim 行程，也就是 Omniverse Kit；右邊是一般的 ROS 2 程式。它們只透過 DDS 網路溝通。

最容易誤解的一點：Isaac Sim 裡並沒有一段 Python 在「收 /cmd_vel、算輪速」。02_run_sim_ros2.py 的主迴圈只有一行： simulation_context.step(render=True)。訂閱、差速運算、寫入 PhysX、發佈 /odom，全都是 OmniGraph 節點（C++）在每次 Kit update 裡完成。 所以要改機器人的「行為」，應該改 ros_graph.py 建出來的 graph，或者在 graph 外另寫 ROS 2 節點，而不是在主迴圈裡加 Python。

03啟動順序：run\sim.cmd

由上往下依序執行。三條泳道分別是 Shell、你的 Python、Kit runtime。紫色箭頭表示 Python 呼叫 API，讓 Kit 端產生實際效果。

為什麼順序不能換

  1. 第 4 步必須在第 5 步之前。apply_ros2_process_env() 把 bridge/humble/lib 放進 PATH 和 DLL 搜尋路徑。如果順序反過來，bridge extension 載入時找不到 DDS 函式庫，publisher 會靜默失效，而不是報錯。
  2. 第 5 步之前不能 import omni.* / pxr / isaacsim.*。這些模組是 Kit 啟動後才存在的，所以程式碼裡 import omni.usd 都寫在 app.launch() 之後，ros_graph.py 等模組也是在這之後才 import。
  3. 第 10 步必須在第 11 步之前。ROS2RtxLidarHelper 需要 lidar 的 render product 路徑，這個路徑是 sensors.py 用 Python 先建好的。相機的 render product 則由 graph 裡的 IsaacCreateRenderProduct 自己建立。
  4. 每步之間的 simulation_app.update()是讓 Kit 跑一幀，讓 extension 啟動完成、stage 和 RTX sensor 準備好。GUI 模式不能呼叫 update()，所以改用 await next_update_async()。
  5. 第 12 步的 physics_dt 要跟第 8 步寫入 PhysicsScene.timeStepsPerSecond 的值一致，兩者都來自 .env 的 PHYSICS_HZ。

05一幀之內：時間是怎麼推進的

PHYSICS_HZ=60、RENDER_HZ=30，所以一次 step(render=True) ≈ 33.3 ms 模擬時間，裡面有 2 次 PhysX substep、1 次 graph 評估和 1 次 RTX render。

對 digital twin 的意義：如果需要每個 physics step 都更新控制（例如高頻伺服），可以把 graph 的觸發源從 OnPlaybackTick 換成 isaacsim.core.nodes.OnPhysicsStep，或者在 Python 端用 SimulationContext.add_physics_callback()。 另外，step() 不會自動對齊牆上時間：GPU 夠快時模擬可能比真實時間快，太慢時則會變慢。需要時間同步的應用，請讓 ROS 端使用 /clock（use_sim_time）。

這就是 Isaac 端的「ROS 節點」。它是 /World/ROS2Graph 底下的 prim，執行時可以用 Window ▸ Graph Editors ▸ Action Graph 打開，即時修改參數。

07按下 WASD 之後的訊號流

以按 W W A 為例，追蹤每一站的實際數值（r = 0.10 m，L = 0.44 m，都來自 .env）。

互動示範：用跟 teleop_key.py 一樣的規則算一遍點一下這個框再按 W A S D / 空白鍵，或直接點按鈕
② linear.x+0.00 m/s
② angular.z+0.00 rad/s
⑦ ωL 左輪+0.00 rad/s
⑦ ωR 右輪+0.00 rad/s
⑨ 轉彎半徑 R∞
⑩ /odom 位置(-7.00, 0.00)
理想運動學（不含打滑）。起點 (ROBOT_START_X, ROBOT_START_Y) = (−7, 0)，四周牆面 ±10 × ±6 m。每按一次鍵會「累加並保持」，就像真的 teleop：不是按住才動。

容易踩到的細節

  • 是狀態，不是按住。按一次 W 就加 0.15 m/s 並一直保持，所以要按 SPACE 才會停。
  • 速度會被限制兩次。teleop 先用 MAX_LINEAR_SPEED / MAX_ANGULAR_SPEED 限制一次，DifferentialController 的 maxLinearSpeed / maxAngularSpeed 再限制一次。
  • graph 裡沒有 cmd_vel 逾時機制。ROS2SubscribeTwist 保留的是最後一筆值。teleop 正常結束時 finally 會送出 0；但如果 client 被強制終止，機器人會照最後的速度繼續走。實體機器人都有 watchdog，做 digital twin 時建議在 graph 或 client 端補上。
  • 輪速目標寫進 PhysX，不寫進 USD。在 Property 面板看 left_wheel_joint 的 Drive targetVelocity 不一定會變。要讀即時狀態，請用 Articulation.get_joint_velocities() 或 /joint_states。
  • 非 Windows 的 teleop 會退回 sys.stdin.read(1)，終端機有行緩衝，所以要按 Enter，而且讀取時會阻塞。

08其他啟動方式的差異

每種方式最後都得到同一個 stage 和同一個 graph，差別在誰啟動 Kit、誰推進時間。

方式誰啟動 Kit誰推進時間ROS 2適合
run\sim.cmdSimulationApp()Python 迴圈 step()✔ 自動 play日常開發、CI（--self-test、--headless）
GUI + gui.build()isaac-sim.bat（會自動跑 setup_ros_env.bat）GUI timeline（按 ▶）✔ 按 ▶ 後出現一邊看 stage / Action Graph 一邊調參數
run\scene.cmdSimulationApp()Python 迴圈，依模擬時間計時✘學 USD / 物理；--save 匯出 USD
run\dataset.cmdSimulationApp(headless)rep.orchestrator.step()✘合成訓練資料（沒有 physics 時鐘，以畫質為主）

GUI 模式在程式上的差異（warehouse_amr/gui.py）：Kit 已經在跑，不能再建立 SimulationApp，也不能呼叫 update()。 所以 build() 用 asyncio.ensure_future 把 build_async() 排進 Kit 的事件迴圈，每步之間 await app.next_update_async()。 它也不建立 SimulationContext，物理頻率由 PhysicsScene.timeStepsPerSecond 決定。[gui] 訊息與例外會出現在 Console，不在 Script Editor 的輸出窗格。

09往 digital twin 發展：要改哪裡

這個 repo 目前是「sim 當作機器人」。digital twin 還需要反方向，也就是讓真實世界的狀態進到 sim。下圖是建議架構，灰字標示 repo 裡還沒有的部分。

常見需求 → 要改的地方

需求改哪裡注意
換成實際廠區（CAD / USD）scene/warehouse.py：參考 _load_full_warehouse() 的做法，用 reference_asset() 載入一定要 asset_scale_to_meters()（cm 與 m 差 100 倍）和 add_colliders_recursive()，否則雷達看得到牆，車卻會直接穿過去。
換成真的機器人模型用 URDF importer 或官方 USD 取代 build_amr()，回傳同樣的 RobotPathsros_graph.py 的 jointNames、chassisPrim、targetPrims，以及 .env 的 WHEEL_RADIUS / WHEEL_BASE，都要跟新模型一致。可以用 --self-test 的 80–120% 檢查來驗證。
新增一個 topicros_graph.py：在 CREATE_NODES、SET_VALUES、CONNECT 三處都要加（context、tick、timeStamp）同時把它加進 expected_topics()，self-test 才會檢查。topicName 要寫相對名稱（不要以 / 開頭）。
新增感測器sensors.py：建 prim 加 render product，再到 graph 加 Helper 節點frame id 要等於 mount prim 的名稱，並把該 prim 加進 PublishTF.targetPrims。
真機狀態驅動 sim（影子模式）新增 graph 分支：ROS2SubscribeJointState 接 ArticulationController（位置或速度模式），或者寫一個 Python physics callback，用 set_world_poses 設定底盤位姿要關掉原本的 /cmd_vel 路徑；時間戳要處理真機與 sim 的時鐘差。
多台機器人把 build_amr(root_path=…) 和 build_ros2_graph 參數化（graph 路徑、namespace 各一份）目前 GRAPH_PATH 是常數，/tf 也會帶 namespace，需要自行決定 TF 的前綴策略。
接 Nav2在 WSL2 或另一台機器啟動 Nav2，使用同一個 ROS_DOMAIN_ID介面已經齊全（/scan /odom /tf /cmd_vel /clock）。記得設 use_sim_time:=true，並加上相機 optical frame 的靜態 TF。
在 sim 裡跑自訂 Python 邏輯simulation_context.add_physics_callback()，或是寫在 02 的主迴圈讀狀態要用 isaacsim.core.prims.Articulation / RigidPrim，不要讀 USD transform。

10必守規則（違反時多半是靜默失敗）

  • 先 SimulationApp()，再 import omni / pxr / isaacsim。這些模組是 Kit 提供的。
  • 先設定 ROS 2 環境，再啟用 bridge。否則 publisher 不會報錯，但也不會送出任何資料。
  • 沒有 play 就沒有 topic。timeline 停止時，DDS 上完全看不到這個 sim。
  • 讀物理狀態用 tensor API（或 /odom），不要讀 USD。播放時，物理結果寫在 Fabric 裡，USD 上的 transform 可能是舊的。
  • 輪子 joint 不要設定 limit；輪子形狀用 capsule，不要用 cylinder。前者會把 joint 鎖死，後者會讓輪子陷進地板。這兩種情況下，上游訊號看起來都完全正常。
  • .env 的輪徑、輪距要跟模型一致。不一致時 /odom 跟實際移動會有落差，self-test 會回報 FAIL。
  • frame id 等於 prim 名稱。改了 prim 名稱，就要一起改 frameId。
  • DDS domain 只看 .env。useDomainIDEnvVar=False，client 也用 rclpy.init(domain_id=…)，所以 shell 裡的 ROS_DOMAIN_ID 不會生效。
